# Task record

Use one record per qualifying task to retain its evolving questions, answers, decisions, and current state across clients and worktrees. It is a personal working record, not a message to a teammate or proof that a source was verified. This skill preserves task context; the active workflow and repository instructions govern branches, implementation, verification, and publication. Read [the record format](references/record-format.md) when creating or restructuring one.

## Find or create

After the active repository's identity checks, derive `{repo}` from the subject repository's verified Git remote name. Search its default `~/Documents/task-records/{repo}/` folder and any known qualified folder for the same remote by task or issue ID, title, feature, and aliases before creating anything. Compare the credential-free remote identity recorded in candidate records with the subject remote; never select a record from a branch name alone. If distinct remotes share a repository name, keep existing paths and use the stable namespace-qualified folder key defined by shared guidance for the other repository. If that guidance is unavailable when a collision needs disambiguation, ask for the folder policy rather than inventing a key. If several records plausibly match or an existing folder's identity remains unclear, resolve the ambiguity before writing. If the subject remote or task identity cannot be established, ask for the missing fact instead of inventing a path.

When a record is created or reused, identify it briefly in normal progress reporting. Do not send a separate notice merely to say that no record is needed. A failed narrow search is not proof that no record exists; inspect the repository's record directory and relevant aliases before creating one.

Create a record when the user asks, when work awaits an answer from another person or system that affects the task, when a choice's rationale will matter beyond this session, or when work is likely to resume in another session. Leave self-contained work without a record when its relevant context is recoverable from the request, repository, and Git. Use a verified issue/task ID as the filename key when available; otherwise choose a short stable task slug, adding a creation-date suffix only to resolve a collision. Keep that path stable as branches and status change; client session IDs are optional source references, not task keys. Do not copy legacy `.task-continuity/` files wholesale; reconcile any useful facts with current sources first.

## Look up an earlier decision

For a read-only question about why a choice was made, a repository identity already recorded in available context can guide the search; creating or updating a record requires verification against the current subject repository. Search matching default and qualified task-record folders by task ID, feature, decision terms, and aliases, including completed records. Read plausible matches and follow their cited original messages, tickets, documents, or commits when accessible. Distinguish a recorded rationale from independently verified evidence; label a missing source or stale claim. If several decisions plausibly match, resolve which one the user means. If no record is found, report the searched scope and continue with relevant Git or project sources rather than treating a narrow search as proof that no decision exists. Do not create a record merely to answer a historical lookup.

## Reconcile and update

- Treat the record as the durable personal history of task questions, decisions, and rationale, not authority over current repository state, external requirements, or approvals. Check its checkout, branch, HEAD, uncommitted paths, verification, and next action against current Git and files before relying on them. Check an external answer against its original message, ticket, or document when available. Label inaccessible or unverified sources; do not turn a summary into an approval claim.
- Update at material boundaries: a question or answer, a consequential choice, a blocker or ownership change, a meaningful verification result, delivery, or a change to the first unfinished action. Do not rewrite it after every turn.
- Record a question with its owner and source; add the dated answer and source when received. For each consequential decision, keep the chosen behavior, rationale, evidence, date, owner when known, and implementation reference. Refer to a sourced answer by its question ID instead of copying it into the decision; when an answer is the whole choice, one entry is enough. Preserve resolved questions and decisions; mark superseded decisions and link their replacements instead of erasing why they were made.
- Immediately before saving, compare the record with the version used for the edit. Reconcile new, non-conflicting content and resolve contradictions rather than silently overwriting another session's change. This is best-effort conflict detection, not an atomic write; when simultaneous writers are likely, coordinate one writer or resolve the conflict before retrying. Keep secrets and unnecessary private conversation out of the file.
- Keep the record focused on durable context and the next meaningful resumption action. Do not copy transient implementation plans, exhaustive checklists, or details readily recoverable from Git.
- Link relevant task materials, reusable test inputs, human-facing handoffs, issues, and PRs/MRs in the record's Related artifacts section with each link's purpose. Keep the source artifact in its own home; do not copy its content into the record.
- Pin verification to the command or observed check, date, and commit or working-tree state. Mark unrun checks pending. If publication remains in scope, retain the intended target, verified base ref and commit, and redacted remote identity; recheck them before publishing under the active delivery workflow.
- At completion, record the outcome and relevant commit or PR/MR, classify deferred dependencies and unresolved decisions with an owner and reopening trigger, and retain the record. Pending questions stay in Questions and answers; Follow-ups contain actionable post-delivery work or externally owned dependencies, referring to question IDs when useful. Link an external follow-up or human-facing handoff when one exists; do not invent one. Do not delete the record merely because the task is done.

When another session continues, point it to the record and have it repeat the identity, Git, source, and material checks. If that session cannot access the file, share the relevant record content explicitly and label it unverified until the receiver reconciles it. Do not create a second handoff snapshot for the same task.
